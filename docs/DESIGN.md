# 界面方向：Liquid Glass 与信息架构

[English](DESIGN.en.md)

本文记录界面的设计依据、当前违例和迁移顺序。它不是规范汇编，只写这个应用要遵守的少数几条，以及为什么。

## 一、Liquid Glass 只属于导航层

Apple 的原话是：玻璃材质留给「浮在内容之上的导航层」。因此：

| 用玻璃 | 不用玻璃 |
| --- | --- |
| 底部浮动栏、搜索球 | 漫画卡片、章节列表、正文 |
| 工具栏按钮、胶囊形控件 | 海报网格的每一格 |
| 面板、菜单、弹窗的容器 | 整页背景 |

判定方法一句话：**它承载内容，还是承载操作**。承载内容的保持实心；承载操作的浮起来。

两条禁令：不把两块玻璃叠在一起（互相折射，都读不清）；不用玻璃铺满整屏（正文的对比度会掉到读不了）。

## 二、迁移前的实际状态

部署目标是 iOS 26，`glassEffect` 无需可用性判断，但界面此前**一处都没用**它，全部是 `.ultraThinMaterial`——那是 iOS 15 时代的毛玻璃，散射光而非聚光。

具体违例：

| 位置 | 问题 |
| --- | --- |
| 首页卡片的 `.glassCard` | 玻璃用在了内容层 |
| 海报格的胶囊角标 | 同上，且与卡片玻璃叠在一起 |
| 浮动栏与搜索球 | 两块独立的材质，中间有缝 |

## 三、迁移顺序

1. **设计系统立规矩**：一个 `glassControl` 只给浮动控件用，注释写明为什么不给内容用。
2. **浮动栏改成一个玻璃容器**：栏与搜索球同属 `GlassEffectContainer`，读作一块材质。
3. **胶囊控件去材质**：未填充的胶囊改为玻璃，填充的胶囊改为强调色（颜色传达动作，不用材质传达）。
4. **内容层回归实心**：卡片、角标、列表行改回实心表面，只保留阴影与圆角。
5. **逐屏核对对照度**：正文 4.5:1，控件 3:1；在浅色、深色、彩色壁纸下各看一次。

前两步已完成，后三步待做。这一步之所以先做设计系统而不是逐屏改，是因为没有统一入口时，「玻璃」会顺着复制粘贴长回内容层。

## 四、信息架构里不该出现的词

界面此前把实现模型直接摊给了用户：组件、模块、插件、布局、模板。这些词描述的是代码怎么组织，不是用户要做什么。

替换原则：**用用户的目的命名，不用我们的结构命名**。

| 现在 | 应该是 |
| --- | --- |
| 模块 | 直接列出内容：阅读、观看、收藏、下载 |
| 插件 | 源、供应商（用户能理解的名词） |
| 模板、布局 | 首页卡片、排序 |
| 组件 | 首页的某一块内容，用它的标题称呼它 |

这条尚未落地：需要先在界面上确认这五个词各自出现在哪一屏，避免改错地方。

## 五、外观要能装

最初设想的外观是可安装的内容，不是写死的配色。此前内置过「Miuix」与「Miuix 深色」两套，但内容没人用，已移除：现在内置只剩「跟随系统」，其余主题一律靠安装。

目标形态：

| 能力 | 说明 |
| --- | --- |
| 主题即数据 | 已有：一个 JSON，含强调色、背景、圆角、明暗 |
| 从链接安装 | 待做：粘贴一个 `.json` 链接即可安装，和装源同一个入口习惯 |
| 主题列表 | 待做：整理若干套真正可用的主题（含完整配色，不只是换强调色） |
| 订阅更新 | 待做：主题带 `url` 时可检查更新，复用源的批量更新 |

关键判断：主题是**内容**而不是插件。它没有行为，只有数据，所以安装路径应当是「装一个文件」，不需要打包成插件、也不需要执行环境。

## 六、动效：少、短、可关

参考站点 https://liquidglassdesign.com/ 是视觉画廊，收录的是液态玻璃的界面与动效**作品**，没有可抄的参数或代码；权威依据仍是 Apple HIG 与 SwiftUI 自己的动画 API。这里只写这个应用采用的少数几件。

| 规则 | 理由 |
| --- | --- |
| 只动 transform 与 opacity | 动模糊半径、阴影半径、几何尺寸会重绘整层，滚动时掉帧 |
| 时长 0.2–0.35 秒，弹簧用 `.snappy` | 再长会显得迟钝，再短看不清发生了什么 |
| 位置变化用一条几何过渡，而不是两条交叉淡入 | 两个图层互相对着动，观感是抖的，代价也是两倍 |
| 循环动效只用于「可以拖动」提示 | 常驻循环动画最耗电，也最容易让人分心 |
| 尊重「减弱动态效果」 | 开启时抽动停止、选中胶囊直接到位，不做位移过渡 |
| 不为长列表逐项加入场动画 | 首屏一帧内触发几十个动画，正是启动卡顿的来源 |
| 动效不承担信息 | 关掉动效后每个操作仍然看得懂 |

已落地：选区胶囊用一条 `matchedGeometryEffect` 过渡（0.28 秒 `.snappy`），编排时的抽动受「减弱动态效果」约束。

## 七、宽屏与折叠形态

iPhone Duo 这类设备展开后是接近平板的宽度，两列栅格会显得空旷，卡片也被拉得过高。因此：

| 宽度 | 列数 |
| --- | --- |
| 紧凑（手机竖屏） | 2 |
| 常规（展开形态、iPad 竖屏） | 3 |
| 更宽（iPad 横屏、分屏） | 4 |

判断依据是可用宽度而不是设备型号：折叠、分屏、台前调度都会改变宽度，而型号不会。卡片的「小/中」含义随之变化——小占一列，中占两列。

## 八、一个视图只能有一个弹窗

SwiftUI 每个视图只保留**一个** `.alert`，多出来的会被静默丢弃——不报错、不警告，只是永远不出现。

这个坑在本项目里已经出现过三次：设置页（加「从链接安装主题」时）、漫画详情页（标签提示与下载提示）、环境页（新建与重命名）。三次都是"功能写了、界面从不显示"。

规则：**同一视图上的提示合并成一个状态**——用一个可选的说明文字，或一个枚举，而不是并列两个 `.alert`。真的需要两个提示时，把其中一个挂到**另一个子视图**上（例如列表自己、而不是外层导航栈）。

没有把它做成自动检查：静态扫描分不清"同一条修饰链上的两个"与"两个子视图各一个"，而误报挡住 CI 比不查更糟。这条只能靠人和评审记住。


## 九、`Menu` 的标识符会被丢掉

给 `Menu` 的 label 挂 `accessibilityIdentifier`，界面上那个按钮**看得见、点得动**，但无障碍树里没有这个标识符。于是同一条链上「隐藏」按钮（普通 `Button`）有名字，旁边「大小」菜单没有——测试报「编辑没有进入编排」，而实际上编排早就进去了。

判断依据是这类失败的样子：按钮文案已经变成「完成」、卡片上多了「隐藏」，说明状态切换成功，缺的是**名字**而不是行为。

规则：需要被测试或 VoiceOver 按名字找到的控件，用 `Button` 挂标识符；要二级选项就用 `Button` + `.confirmationDialog`，不要用 `Menu`。`Menu` 只用在「找不到也无所谓」的地方。

这类缺陷不会被编译发现，也不会被静态检查发现——它只在真机/模拟器的无障碍树里现形，所以界面用例失败时**先读树**，再判断是实现坏了还是断言找错了东西。
